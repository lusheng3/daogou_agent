# 技术决策

## D-001：先 Spec 后代码

状态：已采纳

决定：

- 每个模块编码前先完成五份 Spec。
- 关键问题未关闭时停止编码。
- 实现中发现 Spec 缺口时先修改 Spec。

原因：

- 避免 Agent 自行猜测业务规则。
- 保持任务范围和验收条件清晰。
- 方便面试时解释设计演进。

## D-002：模块化单体

状态：已采纳

决定：

- 第一阶段使用单一 Spring Boot 应用。
- 按业务能力划分模块和代码包。
- 暂不拆微服务，暂不创建 Maven 多模块。

原因：

- 个人全栈开发需要控制部署和联调成本。
- 当前业务边界仍会随 Spec 调整。
- 模块化单体足以展示边界设计。

## D-003：Java 21 + Spring Boot 3.x + Maven

状态：已采纳，精确版本待定

原因：

- Java 21 是长期支持版本。
- Spring Boot 生态适合 REST、SSE、数据库和可观测性。
- Maven 配置直观，适合单应用。

## D-004：自建最小 Agent Runtime

状态：已采纳

决定：

- 不直接依赖 LangChain4j 或 LangGraph。
- 实现受控的 Workflow + ReAct。
- 明确模型调用、工具调用和 Token 预算。

原因：

- 项目需要展示运行时控制能力。
- 面试追问集中在循环、预算、Observation 和收束。
- 自建最小运行时可以减少框架黑盒。

## D-005：存储分工

状态：已采纳

决定：

- MySQL 保存业务事实、会话、展示、偏好和操作记录。
- Redis 用于热数据、短期状态和后续限流。
- Milvus 保存知识块向量索引。

原因：

- 精确事实和事务更新使用关系数据库。
- 语义召回使用向量检索。
- 不把所有数据都塞入向量库。
